# API contracts

Base: `/api/v1`. JSON over the same HTTPS origin; single-user cookie sessions. Zod operation contracts in `@financial-tracking/contracts` define inputs, responses, pagination, errors, and the OpenAPI inventory. Nest DTO adapters stay in the API. The frontend imports schemas/types directly and validates responses rather than maintaining generated duplicate types.

All implemented operations are checked against the inventory at application startup. A global response interceptor validates/strips controller results. OpenAPI 3.1 is generated from those schemas, with registered paths, success/error statuses, query/path inputs, cookie auth, and CSRF headers. Custom Zod refinements (for example date ordering and BIGINT bounds) are enforced at runtime even where JSON Schema cannot express them.

Run `DATABASE_URL=<local-url> node apps/api/dist/export-openapi.js` after building to write `openapi.json`; optionally set OPENAPI_OUTPUT to a destination. Export does not execute startup recovery. No unauthenticated Swagger route is exposed.

- Authentication: POST `/auth/login`, GET `/auth/session`, POST `/auth/logout`, POST `/auth/password`. Login requires the configured Origin; authenticated writes also require X-CSRF-Token. Password change requires the old password and revokes every session.
- Ledger: accounts, balances, transactions, bulk category assignment, categories, transfer linking/unlinking, monthly analytics, and bank connections.
- Reserve metadata: PATCH `/accounts/{id}/presentation` accepts only `{reserveEligible:boolean}`; enabling requires EUR and never changes imported account/balance fields. GET `/reserve-goal` and PUT `/reserve-goal` (only positive exact `targetCents`) return the saved target, server observation time, explicit designations, excluded inactive/non-EUR accounts and dated source components. Progress uses the latest BOOKED observation of each explicitly designated active EUR account, with deterministic timestamp/ID ordering. AVAILABLE values never substitute; missing values stay null, zero/negative values stay signed and observations older than 48 hours are labeled stale. The exact known sum is nullable when no source is observed; COMPLETE means every eligible account has a booked observation, independently of freshness. No derived balance is stored and GET does not create metadata or financial history.
- Imports: CSV preview/commit, recent history, individual run status, unresolved issues, explicit duplicate decisions, manual bank start, challenge continuation, cancellation.
- Contract calendar: GET `/contracts/calendar` requires inclusive `from`/`to`, at most 36 calendar months, and optional `accountId`. It reuses existing anchored recurrence and effective revisions in one repeatable-read snapshot; no transactions are generated. Explicit account scope includes only contracts bound to that account; unbound contracts contribute only globally. Response echoes scope, exact decimal-string `totalPlannedCents`, every requested due-month total/count and date-ordered events with separate linked actual amounts, booking dates and source. Missing links mean unknown payment attribution, never proof of nonpayment. More than 10,000 matching contracts or occurrences rejects with 413 rather than silently truncating. Group scope is integrated by T038.
- CSV rollback: GET `/imports/{id}/rollback-preview` returns an opaque impact token, owned/shared/uncertain/manual/linked counts and at most 100 explanatory rows (counts include all rows). POST `/imports/{id}/rollback` requires `{token, confirm:true, linked:'KEEP'|'REMOVE', confirmLinks:boolean}`; KEEP is the default. REMOVE requires explicit link consent if linked rows are deletable. Only completed/partially successful CSV runs are eligible. A changed snapshot returns 409 `ROLLBACK_STALE`; invalid link consent returns 422. Atomic execution removes only provably owned rows, preserves shared/uncertain rows and retained canonical references, dissolves selected transfer groups without deleting opposite bookings, and never deletes contracts. The run/staging/issues are removed; later requests for that removed run return 404. It does not restore historical financial values on retained records.
- Contract monthly plan: authenticated GET `/contracts/summary` returns `asOf`, count, total `monthlyCents`, per-contract rounded monthly cents and category/kind groups with exact matching `contractIds`. Only contracts valid today and today's effective rules count. Each amount/interval is rounded half up to cents; groups/total sum those same values. Aggregate strings can exceed a row BIGINT. These are forecasts, never actual expense analytics.
- Suggestion decisions: GET `/contracts/suggestions?dismissed=true` lists currently eligible dismissed patterns; the default excludes dismissed/confirmed signatures. PUT `/contracts/suggestions/{key}/decision` accepts `{decision:'DISMISSED'}`; DELETE restores a rejection. The key is a 64-character lowercase SHA-256 hash of normalized provider/account/exact amount/rhythm, not a UUID. PUT/DELETE require the same Origin/cookie/CSRF protections as other writes. An optional `suggestionKey` on POST `/contracts` atomically validates/accepts a current proposal; repeating a confirmed key returns its existing contract. Stale proposals return 409 `SUGGESTION_CHANGED`. Contract deletion clears its acceptance decision while retaining the established auto-link block on explicitly unlinked old payments.
- Bank setup: authenticated GET `/bank-setup` returns `configured`, supported `bankCode` and missing `PRODUCT_ID` / `BANK_ENDPOINT` requirements. It returns no endpoint, product identifier or credentials. Configuration does not establish real bank compatibility.
- Challenges share one Zod definition for `TAN`, `APP_APPROVAL`, `SELECT_METHOD` and `SELECT_MEDIA`. Offered methods can describe media/requirements; a media challenge lists actual offered names. Continuation accepts only offered methods/media. PIN/TAN and challenges are transient; raw bank protocol metadata is not cached.
- Amounts: decimal integer-cent strings backed by PostgreSQL BIGINT. Dates: YYYY-MM-DD; timestamps: UTC ISO-8601. Unknown balances are absent, never synthesized as zero.
- Transaction pages: cursor sorted by bookingDate/id descending; default 50, maximum 100. History and issue lists are bounded to 100 and 1,000 respectively; resolve displayed review entries and reload for subsequent entries.
- CSV preview response samples the first twenty valid rows; all accepted normalized rows are staged in PostgreSQL. Invalid rows require explicit partial-import consent. Completed/ambiguous review data is independent of the original upload, which is not retained.
- CSV mapping accepts optional `descriptionFallback`: only an empty trimmed `description` uses that explicitly mapped source column. Both empty remains an invalid row; no account/counterparty/type label is invented. Old requests without the optional field retain their behavior. Heading suggestions pair an unambiguous payment-purpose and booking-text column; ambiguous alternatives remain manual choices.
- The bounded issue window returns actionable duplicate reviews first, then fills remaining places with row diagnostics. Resolving displayed reviews makes subsequent reviews reachable even when more than 1,000 CSV errors exist.
- A transaction annotation patch validates the requested category and changes transfer groups/counterparts in one serializable database transaction. Rejected input or a failed final write leaves all annotations unchanged.
- Added account PATCH bankConnectionId for explicit reassignment of an IBAN-bearing CSV account to a FinTS connection. Bank import refuses silent cross-connection IBAN duplication.

## Stage 1 accountless CSV and assignment

- UUID inputs are canonicalized to lowercase before comparisons and identity-scope construction. Monetary strings remain exact; references are opaque source values and are not UUID-normalized.
- CSV preview accepts an omitted/null `accountId`; no account or bank connection is created implicitly. Transaction responses can have `accountId: null`. Booked unassigned transactions count globally/monthly. GET `/transactions?unassigned=true` selects them; combining this flag with a specific `accountId` is invalid.
- Identity uniqueness is `(scope, identityType, identityValue)`, independent of nullable account IDs. Existing scopes are backfilled from their original accounts; unassigned imports and explicit separate decisions retain their source scopes. A surviving transaction can retain CSV/FinTS observation identities without duplicating its amount.
- POST `/transactions/assignment-preview`: `{ accountId, transactionIds }`, at most 100 unique source IDs. Returns the current unassigned source, offered target-account candidates, account/source/reference details, bounded candidate-list indicator and a comparison token. The token is an optimistic version hash, not an authentication secret or automatic matching decision.
- POST `/transactions/assign`: `{ requestId, accountId, decisions }`. Each decision contains source `transactionId`, preview `token`, `action` (`BANK`, `CSV`, `SEPARATE`, `SKIP`), optional offered `candidateId`, and explicit `categoryChoice` when nonempty manual categories conflict. Bank/target or CSV financial values may win; categories and transfer flags are preserved by default. Separate keeps both records; skip leaves the source unassigned. Two different existing transfer groups require prior explicit resolution rather than silent unlinking.
- Assignment commits atomically with source identity links and a persistent replay receipt. Identical retries with the same request ID return the committed result; changed payloads, stale comparisons, hidden/cross-account candidates, conflicting aliases or concurrent changes fail safely. One batch cannot apply contradictory overwrites to the same target. Transfer-pair amount/account constraints are checked before changing values or membership.
- Staged import resolutions retain legacy `NEW`/`MATCH`/`SKIP` and add `EXISTING`/`INCOMING`; replacements require the displayed `candidateVersion`. Identical completed decisions replay without decrementing counts twice. The UI offers existing/import values, separate, or skip and exposes differences before confirmation. A known reference whose source fields changed requires review, including purpose/counterparty/value-date changes.
- CSV/FinTS ingestion compares the selected account and unassigned candidates without auto-merging similar rows; unassigned imports can suggest existing assigned records. A confirmed bank observation can reuse the original CSV transaction ID and preserve its manual category while adding real source provenance.

This changes the private v1 consumer contract: older web bundles require non-null account IDs and the old importer cannot write the new required identity scope. Roll out API/web/schema together in a write-paused maintenance window and refresh browser clients before using accountless imports. Do not claim rolling compatibility or blindly roll back an old image; use the compatible pre-update backup when schema/data requires recovery.

The application is a new v1 contract; no historical client compatibility is claimed. No multi-tenant/role model exists in this single-user private application. All financial endpoints require authentication; UI visibility is not an access boundary.

## Category rules and classification

- GET/POST `/category-rules`, PATCH/DELETE `/category-rules/{id}` manage ordered literal rules. `COUNTERPARTY` matches the complete trimmed name, case-insensitively; `DESCRIPTION` matches an explicitly entered literal substring. `direction` restricts income/expense; smaller `priority` numbers win. Equal-priority different-category matches stay unresolved. Disabled categories/rules do not participate.
- Saving rules affects newly created CSV/FinTS transactions only. POST `/category-rules/apply` requires `{ confirm: true }` and explicitly re-evaluates historical non-manual rows. It returns updated, protected and conflicting counts. Former rule assignments can be cleared when no current rule applies; manually assigned or deliberately empty categories remain protected.
- Transaction response adds `categoryOrigin`, `categoryRuleId`, `categoryRuleName`, `categoryRuleConflict` and nullable manual `classification`. Rule ID/name snapshots survive rule deletion. Explicit category changes, including null, set MANUAL and clear automatic attribution.
- POST `/categories/templates` installs selected templates and reuses matching names/suitable known aliases; it never renames existing categories.
- PATCH `/transactions/{id}` accepts nullable `classification`; POST `/transactions/bulk-classification` applies FIXED, VARIABLE or null to 1–100 explicit identities atomically. Null restores automatic fallback: confirmed contract payment is fixed, otherwise unclassified. No monetary value changes.
- Assignment merges retain manual-null categories and origin snapshots. Conflicting manual categories require `categoryChoice`; conflicting manual classifications require independent `classificationChoice`, each CSV or BANK. Rejected merges preserve both source rows and their identities. All operations retain session/CSRF enforcement.

## Contracts and actual-payment ownership

GET/POST `/contracts` list/confirm contracts; GET/PATCH/DELETE `/contracts/{id}` read, edit metadata/term or explicitly delete. DELETE requires `{ confirm: true }` and never deletes actual transactions. GET `/contracts/suggestions` requires two coherent periods with identical provider/amount; reading suggestions performs no writes. POST `/contracts/{id}/revisions` adds an amount/rhythm from an existing future due date; earlier revisions/links remain unchanged. Rhythm is 1/3/6/12 calendar months, anchored to the original start day.

GET `/contracts/{id}/payments?from&to` returns forecast occurrences and actual links separately. POST assigns one real booked non-transfer expense to one due date; any amount/date/provider/account deviation requires `confirmMismatch: true`. DELETE `/contracts/{id}/payments/{paymentId}` removes the link and blocks immediate automatic reassignment. A later explicit manual assignment is allowed. Amounts and forecasts are never adjusted by attributing an unusual payment.

Automatic matching runs after the complete import/assignment batch and confirmed contract changes. Exact provider/amount, optional account, five-day tolerance and unique edges are required. Multiple plausible bookings/contracts remain open. Transaction responses expose the contract ID/name/due-date and an effective FIXED/VARIABLE/UNCLASSIFIED classification; a manual override wins. Bank source overwrites that would change an existing payment's amount/date/provider and competing contract links require explicit unlink/review first. Original source identities and one valid link survive account consolidation.

## Multi-month actual analytics

GET `/analytics/overview` accepts inclusive YYYY-MM-DD `from`/`to`, optional account/category identity or explicit null filters `unassigned=true` / `uncategorized=true`; conflicting identity/null filters are rejected. Default is the last twelve completed Berlin calendar months. At most 36 calendar-month buckets are accepted, including clipped endpoint months. Query refinements and runtime range resolution enforce these bounds before database reads.

Response includes exact integer-cent totals/monthly series, category expenditure shares, fixed/variable/unclassified expenditure, eligible/excluded average months and an optional directly adjacent-month trend. Aggregates can exceed one BIGINT row and remain decimal strings. Average eligibility requires complete selection, a past month and at least one relevant booked non-transfer transaction; income-only months count with zero expenses. Empty/current/future/partial months are disclosed separately. No eligible denominator returns null. Trend cannot skip a gap; zero base returns null percent. Shares/chart coordinates are display-only; money arithmetic and labels retain BIGINT precision.

Transaction queries accept `classification=FIXED|VARIABLE|UNCLASSIFIED` with the same manual-first contract fallback as analytics. All chart/table links retain the report's applied range/account/category, booked-only and transfer-exclusion filters. Unsubmitted filter drafts do not change links under an already displayed report.
