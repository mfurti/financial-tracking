## Integrated concept — 202611180002_workspace_settings

Source implementation only; execution remains limited to disposable PostgreSQL 18 fixtures. The Prisma 7.10.1 schema-to-schema migration adds OwnerProfile, AccountGroup, AccountGroupMember and NotificationAcknowledgement without updating old rows, creating profiles/groups automatically or changing the singleton owner constraint. Existing financial records, reserve metadata and frozen wealth remain authoritative.

Profile names are trimmed and bounded to 80 characters; optional contact email is bounded to 254 and validated by the application, with basic SQL syntax/whitespace protection. Contact metadata never changes username, password or recovery identity. Group names are trimmed/bounded to 60 with nonnegative order and a lower-name unique index; the service additionally owns Unicode case-insensitive name validation and concurrency. Composite membership keys prevent duplication. Group/account removal cascades only membership rows, while existing account relations retain their original deletion rules. Acknowledgements use owner/source composite keys, a 256-character bounded nonblank source key and a timestamp; they never update source imports/contracts. Owner deletion cascades its profile/acknowledgements, without introducing a new owner-management API.

The populated upgrade fixture contains rows in all 22 immediately preceding tables and compares exact server JSON text for every old field, including large signed BIGINT values, original timestamps, import identities, manual annotations, transfer/payment links and frozen components. Existing account reads/writes, clean installation, new keys/bounds/FKs, unchanged singleton/credentials and membership-only cascades are validated. Production volume/lock time and a historical deployed binary remain separate operational/final acceptance evidence.

After separate deployment approval, use the pinned matching migration image through the repository's existing paused-writer backup/restore procedure and run `pnpm db:migrate` once. Verify migration status, original financial rows, unchanged owner identity and initially empty new metadata tables before enabling new writers. Do not replace this SQL with schema synchronization or execute it repeatedly as a backfill. Roll application binaries back only with writes paused and a reviewed compatibility decision; retain the additive tables and recorded metadata. Destructive down migration and shared/production execution are not part of this source task.

## Integrated concept — 202611180001_reserve_wealth

It adds AccountPresentation, ReserveGoal, WealthRecord and WealthRecordComponent, with no alteration/backfill of existing financial columns. The only seeded value is the approved singleton 300000-cent target. No account is automatically designated Tagesgeld and no balance or historical wealth is fabricated.

The generated Prisma 7.10.1 schema-to-schema SQL was reviewed and extended with singleton/positive-target, COMPLETE/PARTIAL and nonblank metadata checks. New retry keys/source labels/types are bounded to 128/120/64 characters without constraining old imported fields. Account presentation cascades only with its account; frozen components keep label/cents/date while an optional deleted account becomes null. Record deletion is restricted while components exist. Application capture is responsible for exact component/total consistency and immutable public behavior; this migration does not claim to protect against arbitrary privileged SQL updates.

Validation uses PostgreSQL 18 through the existing owned test harness: every pre-feature table contains representative synthetic rows, and exact server JSON text compares every old field before/after upgrade without parsing BIGINT through Number. Existing account reads/writes still work. Clean installation, source-balance changes, account removal, unknown versus zero, new uniqueness/defaults/bounds/FKs and existing rollback behavior are checked. A historical deployed binary and production-scale locking/timing are separate final/operator evidence; this local proof does not establish them.

Operator sequence after separate deployment approval: pin the reviewed application/migration artifacts, stop writers, create and verify the approved backup/restore point, run the matching `pnpm db:migrate` migration image once, then start matching API/web and verify original rows plus the singleton goal and empty historical capture. Generate the client with `pnpm db:generate` during artifact preparation, and validate with `pnpm --filter api exec prisma validate`; neither command applies a database migration. Schema-to-schema SQL generation follows the installed [Prisma 7 diff interface](https://www.prisma.io/docs/cli/v7/migrate/diff), without a configured datasource read.

Application rollback must disable the new feature and coordinate writers; retain these additive tables and any newly recorded observations. Do not drop them or promise that a down migration reconstructs later records. A failed/interrupted deployment requires reviewing migration status and the actual schema, then a reviewed forward fix or approved backup recovery. Prisma migration history prevents ordinary reapplication; the SQL file is not a standalone repeatable backfill. Production execution remains unperformed by this task.

## F4: 202611080002_contracts

Adds Contract, time-effective ContractRevision and unique ContractPayment, plus a transaction-level automatic-link block. Forecasts remain derived calendar values and never become bank transactions. Existing financial fields and category/classification metadata remain unchanged. SQL enforces positive forecast amounts, supported intervals, inclusive end ordering, one transaction per occurrence and one contract per actual transaction. Transaction deletion is restricted while linked; service-level contract removal deletes only links/rules and preserves bookings. Old/new mixed writers remain unsupported for attribution semantics; use the same paused-writer migration and recovery gate as F3. F4 was subsequently applied during the approved PR #10 rollout.

Competing links cause atomic rejection before either source is deleted.

## UX1 — 202611080003_import_rollback

Adds nullable creating-import ownership and its index/FK. Conservative SQL backfill requires a single known direct source and transaction creation inside a completed CSV run; ambiguous legacy rows stay unknown. Original monetary fields, timestamps and annotations are unchanged. New ingest records explicit ownership and accountless observations; merged/assigned rows retain source evidence. Rollback is an explicit authenticated/CSRF-protected user action, never migration/startup behavior. It previews protected/manual/linked rows, fingerprints the whole affected state, and atomically removes only owned rows under serializable account/row locks. Retained canonical references remain usable; removed run observations and staging are cleaned. Contract deletion is never implied. Application rollback must still use the paused-writer/compatible recovery procedure.

Initial source verification: actual populated immediately preceding schema upgrade with an exact large BIGINT and unknown-origin record; six dedicated real-database/API/concurrency cases; full 120-case suite before the added sixth case, plus its focused pass; all four desktop/mobile import journeys; lint/types/production builds. The final candidate subsequently passed all eight rollback cases and the complete 131-case main CI. UX1 was applied during the approved PR #11 rollout.

## UX4 — 202611080004_suggestion_decisions

Adds durable hash-keyed DISMISSED/CONFIRMED decisions with a checked state/contract relation. A confirmed decision references its actual contract and cascades only when that contract is removed. No existing financial row is changed. Signatures include normalized provider, account, exact amount and rhythm; further same-pattern payments do not resurrect a dismissal. A changed pattern can reappear. Contract creation validates a current proposal and commits its acceptance/payment matching atomically; repeating an already confirmed key returns the existing contract. PUT/DELETE decisions share authenticated CSRF protection, advisory locking and serializable writes. OpenAPI uses a 64-character hash parameter rather than a UUID. Four dedicated real database/HTTP cases passed, plus existing contract/summarization cases; deletion retains the established auto-link block on old payments. UX4 was applied during the approved PR #11 rollout.
